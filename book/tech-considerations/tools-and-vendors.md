# เครื่องมือสำหรับเทคโนโลยี PQC ในปัจจุบัน

การเปลี่ยนผ่านไปสู่ยุคควอนตัมไม่ได้เป็นเพียงการเลือกอัลกอริทึมใหม่ แต่ต้องอาศัยเครื่องมือซอฟต์แวร์หลากหลายประเภทเพื่อนำระบบรหัสลับสำหรับยุคควอนตัม (Post-Quantum Cryptography: PQC) ไปใช้งานจริงในระบบสารสนเทศขององค์กร ตั้งแต่ไลบรารีระบบรหัสลับพื้นฐาน ไปจนถึงเครื่องมือสำหรับ TLS โครงสร้างพื้นฐานกุญแจสาธารณะ (Public Key Infrastructure: PKI) การทดสอบ และการจัดทำรายการสินทรัพย์ระบบรหัสลับ (Cryptographic Inventory) การทำความเข้าใจภาพรวมของเครื่องมือในปัจจุบันช่วยให้ทีมความมั่นคงปลอดภัยไซเบอร์เลือกใช้เครื่องมือที่เหมาะสมกับบริบท ข้อจำกัดทางเทคนิค และงบประมาณของตนได้อย่างมีประสิทธิภาพ

## กลุ่มของเครื่องมือ PQC

เครื่องมือในระบบนิเวศ PQC ปัจจุบันสามารถแบ่งออกเป็น 7 กลุ่มหลัก ซึ่งแต่ละกลุ่มมีบทบาทแตกต่างกันในวงจรชีวิตของการเปลี่ยนผ่าน (Migration Lifecycle)

### ไลบรารีระบบรหัสลับพื้นฐาน

ไลบรารีระบบรหัสลับพื้นฐาน (Core Cryptographic Libraries) เป็นรากฐานสำคัญที่สุดของระบบนิเวศ PQC ทำหน้าที่พัฒนาอัลกอริทึม PQC ในระดับล่างสุด นักพัฒนาและผู้เชี่ยวชาญด้านความมั่นคงปลอดภัยส่วนใหญ่ไม่ได้เรียกใช้ไลบรารีกลุ่มนี้โดยตรง แต่ได้รับประโยชน์ผ่านซอฟต์แวร์ในชั้นที่สูงกว่า เช่น OpenSSL คุณลักษณะสำคัญของไลบรารีกลุ่มนี้ ได้แก่

- __"ส่วนต่อประสานโปรแกรมประยุกต์ (Application Programming Interface: API)"__: รองรับการสร้างกุญแจ (Key Generation) การห่อหุ้มกุญแจและการถอดกุญแจ (Encapsulation/Decapsulation) และการลงลายมือชื่อดิจิทัลและตรวจสอบลายมือชื่อดิจิทัล (Sign/Verify)
- __"การรองรับมาตรฐาน (Standards Support)"__: รองรับมาตรฐานของ NIST ได้แก่ ML-KEM, ML-DSA และ SLH-DSA และบางไลบรารีรองรับ FN-DSA ตามร่างมาตรฐานแล้ว
- __"การปรับแต่งประสิทธิภาพ (Performance Optimization)"__: บางไลบรารีปรับแต่งด้วยชุดคำสั่ง AVX2 หรือ AVX-512 เพื่อเพิ่มความเร็วบนฮาร์ดแวร์สมัยใหม่

### ไลบรารีโพรโทคอลเครือข่าย

ไลบรารีโพรโทคอลเครือข่าย (Network Protocol Libraries) ทำหน้าที่เชื่อมต่ออัลกอริทึม PQC เข้ากับโพรโทคอลความมั่นคงปลอดภัยที่ใช้งานจริง เช่น TLS 1.3, DTLS, SSH และ IPsec การปรับปรุงไลบรารีกลุ่มนี้จึงส่งผลต่อระบบจำนวนมากพร้อมกัน ประเด็นที่ต้องพิจารณา ได้แก่

- ความเข้ากันได้กับการสร้างกุญแจรหัสลับร่วมกันแบบผสมใน TLS 1.3 เช่น X25519MLKEM768 {cite:p}`rfc10024`
- การได้รับการรับรองตามมาตรฐาน FIPS 140-3 สำหรับอัลกอริทึม PQC (ดู [การรับรองและทดสอบความสอดคล้องของเทคโนโลยี PQC](certifications.md))
- ผลกระทบต่อขนาดของข้อความเริ่มต้นการเชื่อมต่อ (Handshake) ที่เพิ่มขึ้น (ดู [ระดับความมั่นคงปลอดภัยและการวิเคราะห์ประสิทธิภาพ](security-analysis.md))

### ตัวห่อหุ้มภาษาโปรแกรม

ตัวห่อหุ้มภาษาโปรแกรม (Language Wrappers and SDKs) ช่วยให้นักพัฒนาเรียกใช้ฟังก์ชัน PQC จากภาษาโปรแกรมระดับสูงได้โดยไม่ต้องเขียนโค้ดภาษา C โดยตรง ซึ่งช่วยลดความซับซ้อนและความเสี่ยงจากการเขียนโค้ดระบบรหัสลับด้วยตนเอง ภาษาที่มีตัวห่อหุ้มพร้อมใช้งาน ได้แก่ Python, Java, Go, Rust, C# และ JavaScript (Node.js) โดยส่วนใหญ่อยู่ภายใต้โครงการ Open Quantum Safe (OQS) {cite:p}`liboqs2024`

### ระบบ PKI และการบริหารจัดการใบรับรองดิจิทัล

การเปลี่ยนผ่านไปสู่ PQC ต้องปรับปรุงห่วงโซ่ใบรับรองดิจิทัล (Certificate Chain) และ PKI ทั้งระบบ เครื่องมือกลุ่มนี้ช่วยให้ผู้ออกใบรับรอง (Certificate Authority: CA) และระบบบริหารจัดการใบรับรองดิจิทัลออก ตรวจสอบ และบริหารจัดการใบรับรองดิจิทัลที่ใช้อัลกอริทึม PQC หรือแบบผสมได้ ประเด็นสำคัญ ได้แก่

- ใบรับรองดิจิทัล X.509 ที่ใช้ PQC มีขนาดใหญ่กว่าใบรับรองดิจิทัล RSA หรือ ECC หลายเท่า ซึ่งอาจกระทบต่อระบบที่มีข้อจำกัดด้านขนาดข้อมูล
- การรองรับใบรับรองดิจิทัลแบบผสม (Hybrid Certificate) ในช่วงการเปลี่ยนผ่าน (ดู [ระบบแบบผสม](../pq-security/hybrid-impl.md))

### เครื่องมือทดสอบและวัดประสิทธิภาพ

ก่อนนำ PQC ไปใช้งานในระบบจริง องค์กรต้องมีเครื่องมือทดสอบและวัดประสิทธิภาพ (Testing and Benchmarking Tools) สำหรับตรวจสอบความถูกต้องของการพัฒนาอัลกอริทึม (Correctness Testing) และวัดประสิทธิภาพบนฮาร์ดแวร์เป้าหมาย (Performance Benchmarking) โดยเฉพาะในสภาพแวดล้อมที่มีทรัพยากรจำกัด เช่น อุปกรณ์อินเทอร์เน็ตของสรรพสิ่ง (Internet of Things: IoT) เครื่องมือกลุ่มนี้มักมีความสามารถดังนี้

- ชุดข้อมูลทดสอบ (Test Vectors) อ้างอิงจาก NIST เพื่อตรวจสอบความถูกต้องของการพัฒนา
- ผลการวัดรอบการประมวลผล (Cycle Counts) บนสถาปัตยกรรมต่าง ๆ เช่น x86-64 และ ARM Cortex-M4
- การวิเคราะห์ความเสี่ยงต่อการโจมตีผ่านช่องทางข้างเคียง (Side-Channel Analysis)

### เครื่องมือค้นหาและจัดทำรายการสินทรัพย์ระบบรหัสลับ

ก่อนเปลี่ยนผ่านไปสู่ PQC องค์กรต้องทราบว่ามีการใช้ระบบรหัสลับที่ใดบ้างในระบบสารสนเทศ เครื่องมือค้นหาและจัดทำรายการสินทรัพย์ระบบรหัสลับ (Cryptographic Discovery and Inventory Tools) ทำหน้าที่สแกนซอร์สโค้ด ไฟล์การตั้งค่า (Configuration Files) การรับส่งข้อมูลบนเครือข่าย และองค์ประกอบซอฟต์แวร์ต่าง ๆ เพื่อจัดทำบัญชีรายการวัสดุด้านระบบรหัสลับ (Cryptography Bill of Materials: CBOM) {cite:p}`cyclonedxcbom` ความสำคัญในบริบทของประเทศไทย ได้แก่

- ระบบสารสนเทศขนาดใหญ่ในองค์กรไทยมักมีการใช้ระบบรหัสลับกระจายอยู่หลายร้อยหรือหลายพันจุด ซึ่งยากต่อการตรวจสอบด้วยตนเอง
- การจัดทำรายการสินทรัพย์ระบบรหัสลับเป็นขั้นตอนแรกที่จำเป็นในการวางแผนเปลี่ยนผ่าน {cite:p}`nist2024ir8547` ดังรายละเอียดในหัวข้อ [แนวทางการจัดทำรายการสินทรัพย์ทางสารสนเทศ](../guidelines/inventory.md)

### เฟิร์มแวร์และเครื่องมือบริหารจัดการ HSM

โมดูลรักษาความปลอดภัยฮาร์ดแวร์ (Hardware Security Module: HSM) เป็นอุปกรณ์เฉพาะทางที่จัดเก็บและใช้งานกุญแจรหัสลับในสภาพแวดล้อมที่ทนทานต่อการงัดแงะ (Tamper-Resistant Environment) และใช้กันแพร่หลายในสถาบันการเงิน หน่วยงานภาครัฐ และโครงสร้างพื้นฐาน PKI เครื่องมือกลุ่มนี้ครอบคลุมทั้งเฟิร์มแวร์ที่ปรับปรุงให้รองรับ PQC และซอฟต์แวร์คั่นกลาง (Middleware) สำหรับบริหารจัดการ HSM ประเด็นเฉพาะของ HSM ในบริบทของ PQC ได้แก่

- __"ความจุและขีดความสามารถ (Capacity and Capability)"__: HSM รุ่นเก่าจำนวนมากออกแบบมาสำหรับกุญแจ RSA และ ECC พื้นที่จัดเก็บที่มั่นคงปลอดภัยและหน่วยประมวลผลภายในจึงอาจไม่รองรับกุญแจ ML-KEM หรือ ML-DSA ซึ่งมีขนาดใหญ่กว่า
- __"มาตรฐาน PKCS#11"__: PKCS#11 (Cryptoki) เป็น API มาตรฐานสำหรับการสื่อสารกับ HSM ซึ่ง OASIS กำลังขยายให้รองรับอัลกอริทึม PQC ซอฟต์แวร์ที่ใช้ PKCS#11 อยู่แล้วจึงสามารถรองรับ PQC ได้เมื่อ HSM และไดรเวอร์พร้อม
- __"การรองรับของผู้ผลิต (Vendor Support)"__: ผู้ผลิต HSM ชั้นนำ เช่น Thales, Entrust และ Utimaco ได้ออกเฟิร์มแวร์ที่รองรับ ML-KEM และ ML-DSA แล้ว และบางรายได้รับการรับรอง FIPS 140-3 ที่ครอบคลุมอัลกอริทึมเหล่านี้ {cite:p}`thalestct2026fips` ขณะที่ HSM รุ่นเก่าบางรุ่นอาจต้องเปลี่ยนฮาร์ดแวร์ใหม่ (Hardware Refresh)

## โครงการโอเพนซอร์สที่เป็นที่นิยม

### liboqs

liboqs เป็นไลบรารีหลักของโครงการ Open Quantum Safe ซึ่งริเริ่มที่ University of Waterloo ประเทศแคนาดา และปัจจุบันอยู่ภายใต้ Post-Quantum Cryptography Alliance (PQCA) ของ Linux Foundation พัฒนาด้วยภาษา C และเผยแพร่ภายใต้สัญญาอนุญาต MIT {cite:p}`liboqs2024` liboqs รวบรวมอัลกอริทึม PQC ทั้งที่ NIST ประกาศเป็นมาตรฐานแล้วและที่อยู่ระหว่างการพิจารณา โดยมีจุดเด่นที่ API รูปแบบเดียวกันสำหรับทุกอัลกอริทึม ทำให้เปลี่ยนอัลกอริทึมได้โดยแทบไม่ต้องแก้ไขโค้ดในชั้นที่สูงกว่า อัลกอริทึมที่รองรับ ได้แก่

- __"กลไกการห่อหุ้มกุญแจ (Key Encapsulation Mechanism: KEM)"__: ML-KEM, FrodoKEM, BIKE, HQC และ Classic McEliece
- __"ลายมือชื่อดิจิทัล (Digital Signature)"__: ML-DSA, SLH-DSA, Falcon, MAYO และ CROSS

liboqs เป็นฐานของโครงการอื่นในระบบนิเวศ Open Quantum Safe เช่น OQS-Provider และตัวห่อหุ้มภาษาโปรแกรมต่าง ๆ ทั้งนี้ โครงการระบุว่า liboqs มุ่งเน้นการวิจัยและการทดลองต้นแบบ จึงควรประเมินอย่างรอบคอบก่อนนำไปใช้ในระบบใช้งานจริง

### OpenSSL และ OQS-Provider

OpenSSL เป็นไลบรารี TLS ที่ใช้งานแพร่หลายที่สุดในโลก ตั้งแต่รุ่น 3.5 ซึ่งเผยแพร่เมื่อเดือนเมษายน ค.ศ. 2025 OpenSSL รองรับ ML-KEM, ML-DSA และ SLH-DSA โดยตรง และใช้การสร้างกุญแจรหัสลับร่วมกันแบบผสม X25519MLKEM768 เป็นค่าเริ่มต้นสำหรับ TLS 1.3 {cite:p}`openssl35` ประโยชน์สำหรับองค์กรไทย ได้แก่

- ระบบที่ใช้ OpenSSL อยู่แล้วสามารถรองรับ PQC ได้ด้วยการปรับปรุงเป็นรุ่น 3.5 ขึ้นไป โดยไม่ต้องแก้ไขโค้ดแอปพลิเคชัน
- รองรับการเริ่มต้นการเชื่อมต่อ TLS แบบผสม ซึ่งเป็นแนวปฏิบัติที่แนะนำสำหรับช่วงการเปลี่ยนผ่าน

สำหรับระบบที่ยังใช้ OpenSSL 3.0–3.4 หรือต้องการทดลองอัลกอริทึมอื่นนอกเหนือจากมาตรฐานของ NIST โครงการ Open Quantum Safe มี OQS-Provider ซึ่งใช้สถาปัตยกรรมผู้ให้บริการ (Provider) ของ OpenSSL 3 เพื่อเพิ่มอัลกอริทึมจาก liboqs โดยไม่ต้องแก้ไขแกนหลักของ OpenSSL

### PQClean

PQClean เป็นโครงการของชุมชนวิจัย PQC นานาชาติ พัฒนาด้วยภาษา C และ Assembly และเผยแพร่ภายใต้สัญญาอนุญาตแบบสาธารณสมบัติ (Public Domain) หรือ MIT ขึ้นอยู่กับอัลกอริทึม PQClean มุ่งเน้นการพัฒนาอ้างอิงที่สะอาด (Clean Reference Implementations) ซึ่งเน้นความถูกต้อง (Correctness) และความสามารถในการอ่านและตรวจสอบโค้ด (Auditability) มากกว่าความเร็ว โดยกำหนดหลักเกณฑ์การพัฒนาที่ชัดเจน ได้แก่

- หลีกเลี่ยงการจัดสรรหน่วยความจำแบบพลวัต (Dynamic Memory Allocation)
- ทำงานในเวลาคงที่ (Constant-Time) เพื่อป้องกันการโจมตีผ่านช่องทางข้างเคียงด้านเวลา (Timing Side-Channel Attack)
- ผ่านการทดสอบด้วยชุดข้อมูลทดสอบอย่างครบถ้วน

PQClean เป็นแหล่งโค้ดที่ liboqs และไลบรารีอื่นนำไปใช้เป็นฐาน และเป็นแหล่งอ้างอิงสำคัญสำหรับผู้ที่ต้องการตรวจสอบความถูกต้องของอัลกอริทึม

### Bouncy Castle

Bouncy Castle พัฒนาโดย Legion of the Bouncy Castle Inc. ประเทศออสเตรเลีย มีทั้งรุ่นภาษา Java และ C# และเผยแพร่ภายใต้สัญญาอนุญาต MIT เป็นไลบรารีระบบรหัสลับที่ครอบคลุมและเป็นที่นิยมในระบบนิเวศ Java และ .NET มานานกว่า 20 ปี ตั้งแต่ Bouncy Castle Java รุ่น 1.79 ไลบรารีรองรับ ML-KEM, ML-DSA และ SLH-DSA ตามมาตรฐานฉบับสมบูรณ์ของ NIST {cite:p}`bouncycastle2024java179` จุดเด่นสำหรับองค์กรที่พัฒนาระบบด้วย Java หรือ .NET ได้แก่

- รองรับอัลกอริทึม PQC ทั้งใน Java และ C#
- มี API ระดับสูงสำหรับการออกและตรวจสอบใบรับรองดิจิทัล X.509 และการใช้ KEM ร่วมกับ Cryptographic Message Syntax (CMS)
- ใช้งานในระบบองค์กรจำนวนมาก เช่น ระบบธนาคารและระบบบริการภาครัฐอิเล็กทรอนิกส์ที่พัฒนาด้วย Java

### AWS-LC

AWS-LC (AWS Libcrypto) พัฒนาโดย Amazon Web Services ด้วยภาษา C และ Assembly และเผยแพร่ภายใต้สัญญาอนุญาต Apache 2.0 AWS-LC แยกสายการพัฒนา (Fork) มาจาก BoringSSL ของ Google และมีชั้นความเข้ากันได้กับ OpenSSL (OpenSSL Compatibility Layer) AWS ใช้ไลบรารีนี้เป็นฐานของบริการต่าง ๆ เช่น AWS Key Management Service (KMS) จุดเด่นสำหรับองค์กร ได้แก่

- AWS-LC FIPS 3.0 เป็นไลบรารีระบบรหัสลับโอเพนซอร์สรายแรกที่รวม ML-KEM ไว้ในขอบเขตของการรับรอง FIPS 140-3 {cite:p}`aws2024lcfips3` จึงเหมาะกับองค์กรที่มีข้อกำหนดด้านการปฏิบัติตามกฎระเบียบ
- รองรับ ML-DSA สำหรับการลงลายมือชื่อดิจิทัลและการตรวจสอบผ่าน API ระดับล่างแล้ว แต่การใช้ใบรับรองดิจิทัล ML-DSA ในชั้น TLS ยังอยู่ระหว่างการพัฒนา
- มีการปรับแต่งประสิทธิภาพในระดับ Assembly สำหรับทั้ง x86-64 และ ARM64

### pqm4

pqm4 พัฒนาโดยนักวิจัยจาก Radboud University ประเทศเนเธอร์แลนด์ และผู้มีส่วนร่วมจากสถาบันอื่น ด้วยภาษา C และ Assembly สำหรับ ARM Cortex-M4 {cite:p}`kannwischer2019pqm4` โครงการนี้มุ่งพัฒนาและวัดประสิทธิภาพอัลกอริทึม PQC บนไมโครคอนโทรลเลอร์ ARM Cortex-M4 ซึ่งใช้กันแพร่หลายในอุปกรณ์ IoT ระบบฝังตัว และอุปกรณ์อุตสาหกรรม ความสำคัญของ pqm4 ได้แก่

- ให้ข้อมูลประสิทธิภาพ ได้แก่ รอบการประมวลผล การใช้หน่วยความจำสแต็ก และขนาดโค้ด ของแต่ละอัลกอริทึมบน Cortex-M4
- ช่วยให้ผู้ออกแบบระบบ IoT ตัดสินใจได้ว่าอัลกอริทึมใดเหมาะกับข้อจำกัดของอุปกรณ์
- มีการพัฒนาแบบประหยัดหน่วยความจำซึ่งช่วยให้อัลกอริทึมที่ใช้หน่วยความจำมากทำงานบนอุปกรณ์ขนาดเล็กได้

### SoftHSM2

SoftHSM2 พัฒนาโดยโครงการ OpenDNSSEC ด้วยภาษา C++ และเผยแพร่ภายใต้สัญญาอนุญาต BSD 2-Clause เป็นซอฟต์แวร์จำลอง HSM (Software Emulation) ที่รองรับ API มาตรฐาน PKCS#11 ช่วยให้นักพัฒนาและผู้ดูแลระบบทดสอบแอปพลิเคชันที่ต้องใช้ HSM ได้โดยไม่ต้องมีฮาร์ดแวร์จริง และใช้กันแพร่หลายในการพัฒนาและทดสอบระบบ PKI และ DNSSEC ความสำคัญในบริบทของ PQC ได้แก่

- ช่วยให้องค์กรทดสอบการบูรณาการ PQC เข้ากับระบบที่ใช้ PKCS#11 ได้ก่อนจัดหา HSM ที่รองรับ PQC
- ชุมชนโอเพนซอร์สมีโครงการบูรณาการ liboqs เข้ากับ SoftHSM2 เพื่อรองรับการสร้าง จัดเก็บ และใช้งานกุญแจ ML-KEM และ ML-DSA ผ่าน PKCS#11
- เหมาะสำหรับการพิสูจน์แนวคิด (Proof of Concept: PoC) และการทดสอบการบูรณาการ PQC เข้ากับ PKI หรือระบบบริหารจัดการใบรับรองดิจิทัลที่ใช้ PKCS#11 เช่น EJBCA หรือ HashiCorp Vault

```{warning}
SoftHSM2 ไม่มีการป้องกันทางกายภาพใด ๆ กุญแจรหัสลับถูกจัดเก็บเป็นไฟล์บนระบบปฏิบัติการ จึงเหมาะสำหรับสภาพแวดล้อมการพัฒนาและทดสอบเท่านั้น ไม่ควรนำไปใช้ในระบบใช้งานจริง สำหรับระบบใช้งานจริงที่ต้องใช้ HSM องค์กรควรตรวจสอบแผนการรองรับ PQC ของผู้ผลิต HSM ที่ใช้งานอยู่โดยตรง
```
